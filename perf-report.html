Radio4000 — Performance Report

Where the app feels slow, proof it does (or doesn’t), and what to change.

Baseline captured 2026-06-04 · localhost (Vite dev, :5173) vs production (radio4000.com, deployed from main) · test channel /oskar (2 580 tracks) · method: agent-browser automation, see perf/measure.sh.

Read dev numbers with care. Vite serves hundreds of un-bundled module requests in dev, so localhost first-loads are inflated and not representative. Production is the real baseline. The value of showing both: findings that reproduce in both columns are genuine; ones that only show up on localhost are dev-tooling artifacts.

Bottom line: scrolling and ordinary navigation are solid — home, menu, explore, settings and channel revisits all settle fast with no long tasks. Two kinds of friction remain: data loading on first navigation (redundant fetches, empty-state flashes — mostly fixed) and a homepage layout shift (fixed). Findings & proposed fixes

Ordered by leverage. “Before” is measured; “After” fills in as fixes land.

6 · “See all tracks” freezes the main thread ~1.7 s

severe reproduces in prod newly found

Opening a big channel’s full track list (/[slug]/tracks) blocks the main thread in a single ~1.7 s long task — the tab is frozen (no scroll, no clicks) for that whole time. Dead consistent across reps and identical on the PR and on radio4000.com, so it’s pre-existing, not introduced by this branch. The channel landing page is fine because it only renders a 50-track preview; the freeze is specific to the “see all” route.

// SPA nav home → /oskar/tracks (2 582 tracks), worst single long task: PR (less-queries.workers.dev) 1 758 / 1 752 / 1 767 ms (3 reps) prod (radio4000.com) 1 520 ms DOM nodes rendered 2 582 (one full TrackCard subtree each) // main-thread self-time during the freeze (prod CPU profile): 824 ms (program / native layout) 470 ms document.cookie reads 588 ms TrackCard render (app chunk) 457 ms insertBefore 56 ms cloneNode

Root cause: src/routes/[slug]/tracks/+page.svelte passes virtual={false} to Tracklist, so it takes the grouped {#each} branch and mounts a real DOM subtree for every track at once. The 470 ms of document.cookie reads and the layout/paint cost are all downstream of that 2 582-node render storm (posthog autocapture + style/layout reacting to the insertions).

Not a one-line flip. Tracklist can virtualize (its flatItems already interleaves month headers, so grouping survives), but simply setting virtual={true} doesn’t help here: the route scrolls the global .scroll-area, while SvelteVirtualList needs its own height-bounded viewport — measured it still rendered all 2 582 nodes. Making it virtualize means giving the page a bounded flex-column scroll container, and that collides with +layout.svelte’s scroll-restoration (which saves/restores .scroll-area.scrollTop, not an inner viewport). So this is a real design call: (a) restructure the route to virtualize inside its own viewport and move scroll-restoration with it, or (b) incrementally reveal (render ~100, grow on scroll like infinite-grid) — lower risk, keeps document scroll, but Ctrl-F won’t hit unrendered rows.

7 · Pressing play on a big channel freezes the main thread ~1.2 s

severe reproduces in prod fixed ✓

The core action of the app. Hitting play on a large channel — from anywhere (homepage, a channel page, search) — blocked the main thread in a single ~1.2 s long task. Not YouTube: I warmed the YT iframe on a small channel first, then played a 2 582-track channel and it still froze 1 216 ms; replaying the same channel was free. So it was a first-play-per-large-channel cost in our own code.

// play oskar (2 582 tracks), YouTube already warm, worst single long task: prod / PR 1 216 ms small channels (10–14 tracks) 0 ms dev (localhost) 1 871 ms → 0 ms after fix // main-thread self-time during the freeze (CPU profile, YT warm): 1 024 ms TanStack live-query build (e / k / get / has / enrichWithVirtualProps)

Root cause: src/lib/components/queue-panel.svelte resolved the playlist with a live query — useLiveQuery(q => q.from({t}).where(inArray(t.id, trackIds))) — where trackIds is the entire playlist (2 582 ids). inArray() over a multi-thousand-element list rebuilds a whole query collection on every new playlist. The kicker: the queue panel is always mounted (hidden via CSS, not unmounted), so this ran on every play even when the queue was closed and invisible.

Fix shipped: resolve the queue straight from the collection Map — trackIds.map((id) => tracksCollection.state.get(id)) — the exact pattern player.svelte already uses for the same playlist. The tracks are already in the collection, so it’s O(n) Map lookups (instant) instead of building a live-query collection. Dropped the useLiveQuery/inArray imports. Playback (next/prev) was never affected — it reads the id queue directly, not the resolved objects.

Before
~1.2 s frozen tab on every first play of a big channel
After ✓ measured
0 ms long task · queue still renders (windowed) in correct order

Verified: queue panel shows the right tracks newest-first, switching channels updates it, 220/220 tests pass, no new type errors. Same engine as #6 (TanStack materialisation over thousands of rows) — but here it was pure waste (a hidden panel fetching the whole playlist), so it was a clean win.

1 · Redundant data fetches on every channel load

medium reproduces in prod

A single channel visit fires the same queries several times over. Confirmed identical on dev and prod (clean SPA home → /oskar):

rest/v1/channels_with_tracks × 4 rest/v1/channel_tracks × 2 rest/v1/followers × 2 + YouTube thumbnails × ~50 (first 20 eager, rest loading="lazy")

Root cause: src/routes/[slug]/+layout.svelte resolves the channel in two useLiveQuery stages (by slug, then by stable id), and tracks/followers each trigger their own query — keys aren’t deduped, so channels_with_tracks is requested 4×.

Fix shipped: the collection’s idIn queryFn now serves channels already in the collection from cache and fetches only the missing ids (src/lib/collections/channels.ts). This kills the by-id re-fetch of the channel we just loaded by slug, and shrinks follower/following hydration to only the channels we don’t already have.

channels_with_tracks ×4 on every visit
(by-slug + redundant by-id + 2 batches)
After ✓ measured
cold visit ×3 (by-id self-fetch gone)
warm revisit ×0 — fully cache-served

Same channel switching still resolves correctly (Radio Oskar → Nomads Radio, full track counts, no errors). tracks ×2 stays — one full load + one cheap freshness probe (select=updated_at&limit=1); intentional. followers ×2 are embedded-join reads, not channel fetches; deferring them off the home tab is a separate follow-up.

2 · Homepage layout shift (CLS 0.16)

medium reproduces in prod fixed ✓

The logged-out homepage shifts ~0.14 as content settles. The LCP <img> was a red herring — instrumenting the layout-shift sources and tracking element positions over the load pinned the real cause: the featured hero column pops in from 0 → ~450–570px at ~700 ms and shoves everything below (footer + globe) down.

// layout-shift sources at the big shift: [ div.globe , footer.stats.footer-stats ] value 0.1415 // element positions over load (.globe top): t=229ms featured absent globe.top = 470 t=723ms featured = 634px globe.top = 1104 ← +634px push

Root cause: src/routes/+page.svelte — the featured grid is gated on {#if featuredChannels.length} (absent until data loads), and its cards use grid-template-rows: 1fr (src/styles/layout.css:110), so the row height is fluid and non-deterministic — I measured 446px and 566px on different random featured sets.

Fix shipped (matched skeleton): the featured section now always renders — a skeleton that mirrors ChannelCard’s height-driving structure (square aspect-ratio:1 figure + body lines) holds the slot until data arrives, so the real cards drop into reserved space instead of pushing the globe down (src/routes/+page.svelte). Keeps the hero’s fluid look; no visual change once loaded. Verified across viewports (the card height is non-deterministic — descriptions vary — so the skeleton approximates; residual is below the “good” threshold everywhere).

3 · Track list blinks empty on every channel switch

low–medium reproduces in prod

tracksCollection is a single global collection filtered by slug. Switching channels re-runs its queryFn, so its state momentarily empties before repopulating — a flash of “Tracks (0)” / “No tracks yet”.

window.r5.tracksCollection._state.size channel A: 2580 → switch: 0 ← empty flash → repopulate: 2580 (~70–130 ms later)

Root cause: src/lib/collections/tracks.ts (on-demand, slug-filtered) + src/routes/[slug]/+layout.svelte tracks useLiveQuery.

Fix shipped: the tab count now prefers loaded tracks but falls back to the channel’s known track_count while they load, and the header keeps the previously-resolved channel visible during the ~60 ms switch gap (src/routes/[slug]/+layout.svelte). The body already had a “Loading tracks…” guard. Same root fix as #4.

4 · Literal “@unknown / Updated unknown” placeholder flash

low (cosmetic) client-nav path

On client-side channel load, the header shows literal placeholder text before metadata hydrates (~100 ms window on dev/SPA). Production hard-loads hide it via SSR, but in-app navigation still hits it.

t=162 ms @unknown · "Updated unknown" ← flash t=262 ms @oskar · real channel header

Real root cause (found via instrumentation): during a channel switch a single-result live query briefly yields a truthy empty object {}, so pickRouteChannel returned a ghost channel with no name → deckTitle() fell back to the literal '@unknown' (src/lib/deck.ts:8), and the tab read track_count of undefined → 0.

Fix shipped: pickRouteChannel now rejects id-less ghost objects (src/lib/channel-route.ts, + unit test), so channel is cleanly undefined during the gap; the layout then holds the previous channel for presentation until the new one resolves. Header transitions Radio Oskar → Nomads Radio with no “@unknown” frame.

5 · ~50 YouTube thumbnails per channel load

low

Each channel visit pulls ~50 i.ytimg.com/.../mqdefault.jpg images (first 20 eager). It doesn’t cause jank today — scroll stays at 60 fps — but it’s a lot of third-party requests up front.

src/lib/components/track-card.svelte:174 — loading="lazy" only applies when index > 20.

Fix (optional): trim the eager count, and set explicit image dimensions to keep layout work down. Low priority — monitor, don’t over-engineer.

Proven healthy — don’t touch

  • Scroll performance: 2 580-track channel scrolls at a steady 60 fps — worst frame 17 ms, zero long tasks, on both dev and prod.
  • List rendering — where it’s windowed: the channel landing preview (50 tracks) and the queue panel use the virtual list (@humanspeak/svelte-virtual-list), ~110 rows in DOM. Exception: the full /[slug]/tracks route is not windowed — see finding #6.
  • Warm navigation: revisiting a channel settles in 70–130 ms.
  • No long tasks observed in any measured interaction.
  • Collection cache: tracks staleTime 24 h, channels 1 h — sensible; the issue is fetch dedup, not staleness.

How to reproduce

The harness drives a real browser through a fixed scenario and prints JSON. Run it against either base URL to capture before/after numbers:

bun dev # for the localhost run perf/measure.sh http://localhost:5173 # dev numbers perf/measure.sh https://radio4000.com # prod baseline
