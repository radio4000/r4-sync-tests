Open findings & proposed fixes

1 · “See all tracks” freezes the main thread ~1.7 s

severe reproduces in prod

Opening a big channel’s full track list (/[slug]/tracks) blocks the main thread in a single ~1.7 s long task — the tab is frozen (no scroll, no clicks) for that whole time. Dead consistent across reps and identical on the PR and on radio4000.com, so it’s pre-existing. The channel landing page is fine because it only renders a 50-track preview; the freeze is specific to the “see all” route.

// SPA nav home → /oskar/tracks (2 582 tracks), worst single long task: PR (less-queries.workers.dev) 1 758 / 1 752 / 1 767 ms (3 reps) prod (radio4000.com) 1 520 ms DOM nodes rendered 2 582 (one full TrackCard subtree each) // main-thread self-time during the freeze (prod CPU profile): 824 ms (program / native layout) 470 ms document.cookie reads 588 ms TrackCard render (app chunk) 457 ms insertBefore 56 ms cloneNode

Root cause: src/routes/[slug]/tracks/+page.svelte passes virtual={false} to Tracklist, so it takes the grouped {#each} branch and mounts a real DOM subtree for every track at once. The 470 ms of document.cookie reads and the layout/paint cost are all downstream of that 2 582-node render storm (posthog autocapture + style/layout reacting to the insertions).

Not a one-line flip. Tracklist can virtualize (its flatItems already interleaves month headers, so grouping survives), but simply setting virtual={true} doesn’t help here: the route scrolls the global .scroll-area, while SvelteVirtualList needs its own height-bounded viewport — measured it still rendered all 2 582 nodes. Making it virtualize means giving the page a bounded flex-column scroll container, and that collides with +layout.svelte’s scroll-restoration (which saves/restores .scroll-area.scrollTop, not an inner viewport). So this is a real design call: (a) restructure the route to virtualize inside its own viewport and move scroll-restoration with it, or (b) incrementally reveal (render ~100, grow on scroll like infinite-grid) — lower risk, keeps document scroll, but Ctrl-F won’t hit unrendered rows. Target: no task > 50 ms, windowed DOM.

2 · ~50 YouTube thumbnails per channel load

low

Each channel visit pulls ~50 i.ytimg.com/.../mqdefault.jpg images (first 20 eager). It doesn’t cause jank today — scroll stays at 60 fps — but it’s a lot of third-party requests up front.

src/lib/components/track-card.svelte:174 — loading="lazy" only applies when index > 20.

Fix (optional): trim the eager count, and set explicit image dimensions to keep layout work down. Low priority — monitor, don’t over-engineer.

Proven healthy — don’t touch

  • Scroll performance: 2 580-track channel scrolls at a steady 60 fps — worst frame 17 ms, zero long tasks, on both dev and prod.
  • List rendering — where it’s windowed: the channel landing preview (50 tracks) and the queue panel use the virtual list (@humanspeak/svelte-virtual-list), ~110 rows in DOM. Exception: the full /[slug]/tracks route is not windowed — see finding #1.
  • Warm navigation: revisiting a channel settles in 70–130 ms.
  • No long tasks observed in any measured interaction.
  • Collection cache: tracks staleTime 24 h, channels 1 h — sensible.

How to reproduce

The harness drives a real browser through a fixed scenario and prints JSON. Run it against either base URL to capture before/after numbers:

bun dev # for the localhost run perf/measure.sh http://localhost:5173 # dev numbers perf/measure.sh https://radio4000.com # prod baseline

Captures: homepage Core Web Vitals, SPA nav settle (cold + warm), scroll-jank frame stats on a heavy channel, placeholder-flash timeline, and per-load request counts. Numbers wobble a few ms run-to-run — read trends, not last digits.
